# Forward syntax evolution

wasm-git preserves bytes from newer Wasm producers even when it cannot interpret
their grammar. Recognition uses the fullest reviewed decoder, independently of
the selected validation profile. Selecting Core 1, 2, or 3 does not restrict the
physical reader or change an exact byte patch.

Every standard audit report and `features --json` includes `grammar`: the syntax
revision, parser version, upstream commit, recovery policy, and typed IR revision.
These fields identify the interpretation used to produce a report. `validator_valid`
is the pinned validator's answer, not proof that unknown syntax is intrinsically
invalid. The `unknown` evidence status is distinct from `invalid_encoding`,
`invalid_semantics`, and `recognized_but_disabled`.

## Boundaries and unknown syntax

- An unknown opcode, constructor, ordering value, or flag stops interpretation
  at that field. Its suffix is retained as opaque bytes. A familiar byte inside
  that suffix cannot serve as a guessed instruction boundary.
- Recovery requires an independently proven length boundary, such as the next
  framed function body or section. Unknown declaration shapes cannot contribute
  guessed entries to a type, function, memory, or global index space.
- A malformed known LEB or truncated known field can be diagnosed precisely
  only after its start and width have been established. An upstream error string
  alone cannot prove the grammar of an unknown prefix.
- Unknown data remains available to exact forward/reverse diff and patch replay.
  Semantic merge cannot synthesize through untrusted declarations. Whole-input
  selection can still preserve an unknown input verbatim.
- Reserved bits are not presumed to have no operands. When a future proposal
  assigns them meaning, it enters the reviewed grammar through an explicit upgrade.

## Upgrade entry points

`src/grammar.rs` owns the interpretation contract and shared memory-immediate
layout admission. `syntax/grammar-lock.json` records every operator's proposal,
name, operands, visitor, and the hashes of every vendored Rust source, including all section, custom,
component, type, immediate, and validation readers.
`tools/check-grammar.py` rejects additions, removals, changed operands, changed
feature defaults, or changed boundary readers until a new inventory is reviewed.
It never downloads dependencies or updates the accepted lock automatically.

For a parser/proposal upgrade:

1. Pin and verify the new upstream source. Rebase local extension patches and
   update the vendored provenance manifest and `grammar::CONTRACT` together.
2. Generate a candidate under the qualification scratch directory with
   `python tools/check-grammar.py --candidate PATH`. Review its differences
   against the accepted lock before replacing that lock.
3. Add exact feature switches, profile requirements, typed IR operands,
   physical field spans, and shared frontier rules. Extend the fuzzer's witnesses,
   dependency rules, and feature combinations at the same time. Generated
   operator projection macros make unhandled operand shapes compilation errors.
4. Test enabled/disabled behavior, truncation at each new field, unknown selectors
   and flags, framed recovery, and exact reconstruction in both directions.
   Confirm the interpretation of existing test bytes: newly assigned bits may
   require a new truly-unknown fixture, while unchanged unknown bytes must remain
   opaque. Never suppress a failure merely because the upstream parser changed.
5. Run the full qualification, build matrix, and release checks described in
   `RELEASE.eu_US.md`. All runtime tests for this release use the existing 64 GiB
   qualification cgroup and the wasm-fuzzer `.tmp` directory.

## Internal formats and revisions

There is no stable pre-1.0 typed IR or fingerprint ABI. Revision 2 uses one
`MemoryOperand` representation for scalar, SIMD, atomic, and array memory access:
alignment, offset, memory/array target, optional ordering, and optional lane.
Atomic fence ordering is explicit, including sequential consistency. Supertype
lists retain every decoded entry rather than silently selecting the first.
Old derived reports and fingerprints should be regenerated from original bytes.
This release deliberately does not retain duplicate old memory-immediate forms
or promise identical pre-release fingerprints.

Raw module bytes are the authoritative content. The compatibility baseline starts with this release, **0.1.4**. Every future
release must read and apply the `WGTPAT01` patches generated by 0.1.4 and all
subsequent compatible releases, including patches whose payload contains syntax
unknown to the generating decoder. Internal IR changes must never change the
exact reconstructed bytes. Older pre-baseline envelopes are not part of this commitment. Byte patches remain explicitly
versioned; an unfamiliar patch format must be rejected, never guessed. Consumers
of interpretation reports should tolerate added JSON fields and treat unfamiliar
statuses/revisions as opaque. These are different contracts: preserving future
Wasm input does not authorize executing an unknown patch operation.

### Reinterpret old patches with the current decoder

`wasm-git apply base.wasm change.wgp --check` is the read-only patch viewer for
file inputs. It verifies the source hash and every edit, reconstructs the complete
target, then parses both modules with the **current** decoder and regenerates the
audit. No opcode names, operand boundaries, feature claims or cached opaque
classification from the producing version are stored in the patch.

Consequently, a patch containing an instruction unknown to its producer becomes
fully interpretable when the viewer adds that grammar. Its instruction name,
operands, required features and byte spans are recomputed without modifying the
patch. For example, a historical opaque `fe 04` becomes `Pause` in a decoder
supporting acquire-release atomics. Newly assigned memory flags likewise gain
their actual ordering or GC-array operands. Existing CLI regressions require
the patch viewer's audit to equal a fresh comparison of the verified modules.

The matching base module (or a repository revision containing it) is required:
a delta alone does not contain all type declarations, index spaces or unchanged
instruction bytes. Missing context must never be guessed. Each parser upgrade
must additionally check an unchanged patch made by the previous binary: its
previously opaque new syntax must now have the expected instruction and operand
spans, while replayed bytes and patch hashes stay unchanged.

Proposal lifecycle metadata does not determine wire syntax. Known deprecated
encodings with nonconflicting selectors can remain recognized. If a future
revision reuses bytes with a different operand layout, add an explicit named
dialect/revision and require selection where ambiguous; do not choose a dialect
by whichever parser happens to accept the input. This release supports the one
syntax revision disclosed in its grammar contract; it does not pretend to
decode future, unimplemented proposals.

## Cross-version acceptance

`tools/check-syntax-upgrade.py --previous BASELINE_BINARY --current CANDIDATE_BINARY --output SCRATCH`
exercises module-version changes, all Core section IDs, new section IDs, unknown
custom conventions/subsections, and instruction/local/immediate boundaries.
It mutates every payload byte in the section cases. Both binaries create forward
and reverse `WGTPAT01` patches, and both binaries apply every patch. For future
upgrades, use the released 0.1.4 binary (and subsequent released baselines) as
`--previous` and the candidate build as `--current`. The fixed 0.1.4 fixture in
`tests/patch_compatibility.rs` must never be regenerated to hide a failure.
Every result must equal the target's original bytes. Incorrect source bytes must
still fail integrity validation. The candidate audit must retain unknown
frontiers and recover the independently framed following function. Run this
script through the wasm-fuzzer cgroup runner, with all outputs under its `.tmp`
directory. The acceptance script can also compare a saved candidate binary with
a new build before publication; that is a syntax-location regression check,
not evidence about a future release that does not yet exist.

## Hypothetical updates

The same acceptance script accepts `--random-cases`, `--duration`, `--seed`, and
repeatable `--corpus` directories generated by wasm-fuzzer. It cycles through
module headers and every Core section family, selects nested physical fields,
and mutates bytes by insertion, deletion, replacement, bit flips, duplication,
reversal or future selectors. Payload edits rebuild the enclosing section length
where its frame is known. Randomized inputs may represent future syntax or be
invalid under today's grammar; they are not valid-only generator output.
The contract here is exact preservation and bounded, truthful audit evidence.

Every mutation undergoes forward and reverse patch creation/application with
the saved baseline and candidate. Source integrity rejection, report bounds,
and raw evidence bytes are checked too. Seeds, selected fields, exact replacement
bytes, source/target hashes and failure inputs stay in the scratch directory.
`wasm-fuzzer/tools/qualify.py` runs this campaign, valid-only multi-validator checks,
long history replay and every regression together, with combined 10-minute
heartbeats. The first three campaigns each run for at least 30 minutes; all
regular and opt-in regressions must finish. A failure in any campaign stops the
combined qualification.

## Reserved and extension admission sites

`tools/syntax_ports.py` is the reviewed inventory for the syntax-update campaign.
Every inventory entry is mandatory. The report records its encoding, required
selector count, completed cases and distinct selectors. Missing an entry or a
selector fails qualification. The inventory hash identifies the exact tested
catalog. `--quick-ports` is available for smoke tests and is forbidden by the
30-minute qualification gate.

The catalog follows the Core binary grammar for
[modules](https://webassembly.github.io/spec/core/binary/modules.html),
[types](https://webassembly.github.io/spec/core/binary/types.html) and
[instructions](https://webassembly.github.io/spec/core/binary/instructions.html),
plus the pinned proposal readers and the memtag wire namespace. It covers:

- Module versions, all section ID byte values, section sizes and every Core
  section's count or scalar index, including custom, start, data-count and tag.
- Custom names and namespaces, name/linking/dylink subsections, branch hints,
  producers, target features, source maps and debug payloads. These conventions
  remain distinct from the Core grammar.
- Recursive, subtype, shared, descriptor, continuation, value, reference and
  heap constructors; packed storage, mutability and supertype counts.
- Ordinary/compact import discriminators and kinds, export kinds, table
  initializer sentinels, limits flags, global shared/mutability flags, tag
  attributes, element/data segment flags and element kinds.
- Every primary opcode byte, FB/FC/FD/FE/FF subopcode namespaces, each packed
  memtag namespace byte, block/heap/select types, cast flags, exception catch
  kinds and stack-switching handler kinds.
- Scalar/SIMD/lane/atomic/RMW/wait memory flags, memory/array indices, offsets,
  fence and atomic ordering selectors, formerly reserved table/memory indices,
  SIMD lanes, instruction vectors, function sizes and local groups/types.

Every byte selector receives all 256 values in seeded random order. Wider
selectors receive every single-bit value and its complement, integer/LEB
boundaries, and additional seeded random values. Random suffix bytes exercise
unknown operand layouts. All changes undergo the same eight cross-binary patch
applications, source-integrity rejection and bounded evidence checks. Exact
before/after bytes and hashes are saved per case for replay. The independently
randomized field campaign additionally draws from real generated modules in
every Core section family.

This is exhaustive over the listed admission-site families and byte selector
domains, not over the infinite space of possible future grammars or every
32/64-bit value. A newly introduced grammar site must extend this inventory
during the explicit parser upgrade review. Unknown selectors are preserved;
the test does not invent their future semantics or claim they validate today.

## Long replay and history acceptance

`tools/check-history-replay.py` builds a continuous 2,048-edge patch chain from
generated modules and hypothetical syntax variants. Both binaries replay the
whole chain from its original root and reverse it from the final result, checking
every intermediate byte. Each original is also committed to a real repository.
Every historical version and divergent branch tip is checked after repacking,
GC, local clone, bundle import, independent fork and nested fork. Forks must
remain usable after their test-owned source repository is removed.

The default campaign creates 16 independent forks and runs 128-step indexed
cherry-pick, revert and rebase queues. An independent binary encoder supplies
the expected two-parent merge result. Random historical checkout and patch
reconstruction continue for the rest of the timed window. Counts, object IDs,
patch hashes and exact source/target snapshots are retained only in scratch.

The paired release gate runs this history campaign alongside the valid-only and
reserved-syntax campaigns, plus every compiled regression and all 13 explicit
opt-in tests. The latter include the official corpus, uwvm examples/workflows,
extended byte fuzz and both 600-second memtag/debug campaigns. Small chain or
queue settings and shortened opt-in campaigns are smoke tests only; they cannot
pass the 30-minute release gate.
